# Loupehole

![Status: Early Development](https://img.shields.io/badge/status-early%20development-orange)

> ⚠️ **Early-stage project**
>
> This project is in a very early stage of development. While the main structure is mostly finished, all the actual mitigations are not ready yet. Come back in a couple of months (I'm out of Codex tokens) ! :)

Loupehole is a privacy-preserving iOS tweak/library that reduces abusive fingerprinting from native apps and embedded web views. The initial scope is based on the public surfaces demonstrated by [mysk-research/loupe](https://github.com/mysk-research/loupe), plus adjacent iOS fingerprinting techniques that are not yet covered by Loupe.

The central design principle is not "make every device random." The safer target is to make protected apps see a coherent, common, low-entropy device profile. A per-user random pile of values is easy to recognize as synthetic and can become a stronger fingerprint than the real device.

## Wha's inside

Loupehole can be compiled from custom build selections. A selection is a collection of fingerprinting mitigations that produces two deliverables:

- an injectable arm64 iOS dynamic library, which can be injected per sideloaded app;
- a rootless Debian package, that can enable anti fingerprinting system wide (configurable !).

In addition to the mitigation set, a build seed is included in each selection. This seed changes generated names and compile-time policy seed bytes so independently built artifacts do not all share the same static shape.

While build profiles choose which mitigation modules exist in an artifact, the runtime policy then decides whether the selected modules are active for a particular app bundle. This is configurable through a dedicated settings page generated by Loupehole. For the injectable dylib, the runtime policy is simply to include everything that was compiled.

Loupehole does not aim to make every observation random. Its default approach is coherent normalization: values are derived from seed, scope, policy-seed, and state inputs so related API responses remain plausible together. Build variability reduces static repetition between independently built artifacts, while scoped derivation avoids exposing one globally stable replacement value everywhere.

## Project status

The current baseline contains the runtime, generator, rootless package, Settings bundle, scope and seed machinery, state persistence, and verification scripts. Three mitigations are compiled by the default build selection. Their status is **experimental** and their coverage is intentionally narrow.

The broader surface inventory is substantially larger than the implemented set. The [surfaces](docs/surfaces/) folder contains the list of targettable fingerprinting surfaces, while [mitigations](docs/mitigations/) presents the currently implemented mitigations. 

The documentation links below target those final names.

## Build

### Build environment

The canonical build environment is macOS with:

- Xcode and the iOS SDK (the current project baseline records Xcode 26+);
- Theos with an arm64 iOS toolchain;
- `ldid` for dylib signing;
- `dpkg-deb` for package construction;
- Python 3 for generated build inputs;
- standard BSD userland tools used by the verification scripts.

The minimum deployment target in the build is iOS 15. The intended runtime window is iOS 15 through iOS 26. Every OS version, jailbreak, loader, and target app combination remains subject to real-device validation because private implementation details, ABI behavior, and hookability can differ.

### Commands

From the repository root:

```sh
# Generate the selected mitigation graph, build, sign, and copy the dylib.
make

# Build the dylib and run the project verification gates.
make audit

# Generate, build, verify, and copy the rootless package.
make package

# Build with debug-oriented Theos settings, then audit the dylib.
CONFIG=debug make audit

# Remove Theos, package, generated staging, and dist artifacts.
make clean
```

`make` writes `dist/runtime.dylib`. `make package` writes `dist/com.loupehole.runtime_0.1.0_iphoneos-arm64.deb`. The default selection lives in `config/build.default.json`; a different selection can be supplied with `BUILD_SELECTION=path/to/selection.json`.

## Runtime requirements and use

The rootless package is intended for a jailbroken iOS device that has:

- iOS 15 or later within the project’s intended iOS 15–26 range;
- a rootless package environment;
- a MobileSubstrate-compatible injection loader, such as the loader expected by the `mobilesubstrate` package dependency;
- `PreferenceLoader` for the packaged Settings pane.

The package filter starts without a global bundle allowlist. The Settings bundle manages default policy and per-bundle overrides; the runtime still excludes non-app, extension, and system-bundle contexts before seed resolution or hook installation. A package installation alone does not claim that every app, process, or surface is protected.

The standalone dylib is intended for an owned-app test or sideload-style injection workflow capable of loading the library into that app process. It is the same runtime, but package-only configuration and rootless state behavior are not assumed in that mode.

## Safety, scope, and non-goals

Loupehole is focused on reducing fingerprintability, not bypassing DRM, defeating fraud systems, impersonating hardware, or evading an app’s security controls. The project collects no telemetry. It favors a small set of auditable, reversible changes over broad invasive behavior.

An enabled mitigation should preserve ordinary behavior wherever possible, pass through when it cannot safely provide a coherent replacement, and avoid adding project-identifying constants, exports, files, logs, or strings to target app processes.

# Build Configuration

Loupehole uses a static generated build graph for mitigation modules. Mitigations
are not dynamically loaded at runtime. A build selection chooses mitigation IDs,
the generator validates the selection, and Theos compiles only the selected
sources into the injected dylib.

## Files

- `config/mitigations.json`: catalog of every available mitigation module.
- `config/policy-values.json`: catalog of policy values, payload kinds, resolver
  symbols, resolver source files, and derivation label IDs.
- `config/build.default.json`: default local build selection.
- `scripts/build/generate-mitigation-build.py`: validates the catalog and
  selection, then writes generated build inputs.
- `packages/tweak/generated/mitigation-files.mk`: generated Theos source and
  link metadata.
- `core/generated/LHGeneratedMitigationRegistry.h`: generated module IDs and
  registry declarations.
- `core/generated/LHGeneratedMitigationRegistry.c`: generated registry entries
  that call mitigation install functions.
- `core/generated/LHGeneratedPolicyValueRegistry.h`: generated policy value IDs
  and descriptor declarations.
- `core/generated/LHGeneratedPolicyValueRegistry.c`: generated value descriptor
  table that routes policy queries to resolvers.
- `core/generated/LHGeneratedDerivationLabels.h`: generated derivation label
  declarations.
- `core/generated/LHGeneratedDerivationLabels.c`: generated opaque derivation
  label bytes.

Generated files are ignored by git. The root `make` target regenerates them
before compiling. If building directly from `packages/tweak` with Theos, run
`make generate` from the repository root first.

## Catalog Entries

Each mitigation entry has a stable dotted ID and build metadata. Entries may be
method-level components or surface-level composites. A composite is appropriate
when one user-visible mitigation needs several hook adapters to cover real call
paths. Mitigation entries also declare the policy values they need, so the
generator can include only the required value descriptors and resolver sources:

```json
{
  "id": "system.boot_time.composite.synthetic",
  "sources": [
    "packages/tweak/sources/system/boot_time/BootTimeMitigation.m",
    "packages/tweak/sources/system/boot_time/BootTimeSysctlMitigation.c",
    "packages/tweak/sources/system/boot_time/BootTimeProcessInfoMitigation.m"
  ],
  "policyValues": [
    "boot_time"
  ],
  "requires": [],
  "conflicts": [],
  "frameworks": [
    "Foundation"
  ],
  "weakFrameworks": [],
  "libraries": [],
  "minIos": "15.0",
  "maxIos": null,
  "language": "objc",
  "status": "experimental",
  "optionDoc": "docs/options/system-boot-time.md"
}
```

`minIos` defaults to `15.0` when omitted. `requires`, `conflicts`,
`frameworks`, `weakFrameworks`, and `libraries` default to empty arrays.

The catalog intentionally does not include `domain`, `surface`, or `method`
fields. Those are derived from the mitigation ID. It also does not include an
`entry` field: the install symbol is generated by convention.

## Policy Value Catalog

Policy value entries are independent from mitigation IDs, source folders, and
product categories. They describe values that hooks can request from the policy
engine:

```json
{
  "id": "boot_time",
  "kind": "timeval",
  "resolver": "LHPolicyResolve_boot_time"
}
```

The currently supported value kinds are:

```text
utf8_string
timeval
time_interval
```

The generator emits numeric value IDs and a descriptor table from
`config/policy-values.json`. `LHPolicyEngine` uses that generated table to route
`LHPolicyEngineCopyValue` requests. New policy values should be added by
extending the value catalog and adding a resolver, not by adding a new
top-level accessor or switch branch in `LHPolicyEngine`.

`config/policy-values.json` also lists derivation label IDs:

```json
{
  "derivationLabels": [
    "identifier_for_vendor.value",
    "identifier_for_vendor.state",
    "temporal_lifetime.boot_anchor"
  ]
}
```

The build generator hashes each label ID with the configured instance seed and a
versioned build-time namespace, then emits a 16-byte `LHDerivationLabel`
constant:

```text
sha256("lh.derivation-label.v1\0" || instanceSeedBytes || "\0" || labelID)[0..16]
```

If a build selection omits `instanceSeed`, `instanceSeedBytes` is empty for
label generation and runtime state falls back to a random seed. Resolver and
mitigation sources reference generated constants such as:

```c
LHGeneratedDerivationLabel_identifier_for_vendor_value
```

Only generated bytes are compiled into the runtime. The readable label IDs stay
in build configuration and generated symbol names; release artifacts are still
checked by the string and symbol audits. Label IDs are stable API for derivation:
renaming one intentionally rotates the values or state names derived from it.

## ID Convention

Mitigation IDs use this shape:

```text
domain.surface.api_or_method.variant
```

Examples:

```text
identity.idfv.uidevice.scoped_uuid
system.boot_time.composite.synthetic
storage.volume_creation_time.foundation.synthetic
```

Every ID must include a variant segment, even when only one variant exists. This
keeps future variants from forcing ID renames.

## Source Layout

Mitigation source files live below a domain/surface directory:

```text
packages/tweak/sources/<domain>/<surface>/
```

Examples:

```text
packages/tweak/sources/identity/idfv/IDFVMitigation.m
packages/tweak/sources/system/boot_time/BootTimeMitigation.m
packages/tweak/sources/system/boot_time/BootTimeSysctlMitigation.c
packages/tweak/sources/storage/volume_creation_time/VolumeCreationTimeMitigation.m
```

Composite sources should be named after the surface, such as
`BootTimeMitigation.m`. Component adapters should include the API family in the
filename, such as `BootTimeSysctlMitigation.c`. Components that are only used by
a composite are source files, not standalone catalog mitigations.

## Symbol Convention

The generator derives install symbols from IDs:

```text
LHMitigation_ + id with "." replaced by "_" + _install
```

For example:

```text
system.boot_time.composite.synthetic
```

must define:

```c
bool LHMitigation_system_boot_time_composite_synthetic_install(
    LHHookBackend *backend,
    LHPolicyEngine *policy
);
```

The generated registry calls install functions only for selected mitigations.
Mitigation source files should remain thin hook adapters and ask policy APIs for
values once real mitigation behavior is implemented.

Policy value resolver symbols are declared directly in `config/policy-values.json`.
Resolver functions use this signature:

```c
bool LHPolicyResolve_boot_time(
    const LHPolicyEngine *engine,
    const LHPolicyValueRequest *request,
    LHPolicyValueResponse *response
);
```

## Selection Files

A build selection lists the mitigations to compile:

```json
{
  "schemaVersion": 1,
  "target": "ios-arm64-dylib",
  "configuration": "release",
  "minIos": "15.0",
  "instanceSeed": "123e4567-e89b-12d3-a456-426614174000",
  "mitigations": [
    "identity.idfv.uidevice.scoped_uuid",
    "system.boot_time.composite.synthetic",
    "storage.volume_creation_time.foundation.synthetic"
  ]
}
```

Higher-level groups such as "temporal first pass" or "passive MVP" should be
presets that expand into mitigation IDs. A selected mitigation can still be a
surface-level composite when that surface needs several method adapters.

`instanceSeed` is optional and accepts any valid UUID shape; no UUID version is
required. When present, the generator emits the seed as bytes in
`LHGeneratedConfig` and `LHRuntimeConfigDefault` uses it as the runtime default.
When omitted, `LHRuntimeConfigDefault` creates a random runtime seed.

## Validation

The generator checks:

- every selected mitigation exists in the catalog
- every selected mitigation references known policy values
- selected policy values have valid kinds, resolver symbols, and source files
- IDs are stable dotted IDs with at least four segments
- every mitigation lists at least one existing source file
- `requires` dependencies are selected
- `conflicts` are not selected together
- languages and statuses use known values

This catches incompatible build selections before Theos starts compiling.

## Environment

Required local tools should be discoverable through the shell environment:

- `THEOS_HOME`: optional path to the Theos checkout. Defaults to
  `$HOME/theos`.
- `THEOS`: optional explicit Theos path. Defaults to `THEOS_HOME` when set, or
  `$HOME/theos`.
- `PATH`: should include `$THEOS/bin` so Theos helper tools are available.
- `PYTHON`: optional Python interpreter for the build generator. Defaults to
  `python3`.

The root `Makefile` resolves Theos in this order:

```text
THEOS make variable -> THEOS_HOME environment variable -> $HOME/theos
```

Generate build files:

```sh
make generate
```

Build using the default selection:

```sh
make
```

The final signed dylib is copied to:

```text
dist/runtime.dylib
```

Build using a custom selection:

```sh
make BUILD_SELECTION=config/build.default.json
```

Change the destination with:

```sh
make ARTIFACT_DIR=/tmp/loupehole-artifacts
```
